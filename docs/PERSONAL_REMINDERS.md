# Personal calendar reminders

A signed-in participant or staff user can export a generic all-day reminder from an accessible record's next-step area. Export requires an explicitly chosen date and affirmative consent. It rechecks the authenticated actor and realm, exact record and matching current capability version before producing a file. The returned version cannot be older than the displayed record. Access denial, malformed responses and navigation while the check is in flight produce no download. Calendar exports do not mutate case records or contact any calendar provider.

The authenticated read retains its initiating-session check through validation and the final synchronous ICS file callback. A current-session 401 clears private workspace state even when its response body is not JSON. A held successful read or old 401 cannot release a reminder or clear a replacement sign-in. The request's reader context and private record data are used only to verify current access; neither is copied into the calendar file.

Closing the reminder form or record view aborts its pending check and discards its date, consent and prepared bytes. A summary close action cancels synchronously, including a rapid close and reopen before the native toggle notification. Editing, a pending workspace mutation or attachment operation disables the form and cancels its pending output. Actor, realm, session, record and displayed-version changes start a fresh form. The final file callback also checks that the form is still open, so transport completion cannot overtake a queued close notification.

The file contains a generic title and description, chosen date, generation timestamp, independent random event identifier and software identifier. Case titles, record IDs, evidence, names, contact details, location, attendees, organizers and workspace links are excluded. Repeated exports of the same date within the open form reuse the same bytes and event identifier; importer deduplication is not guaranteed. Closing the view discards this memory. No browser storage is used.

The consent text explains calendar-provider/shared-calendar visibility and that imported copies cannot be recalled. `CLASS:PRIVATE` is advisory, not encryption or a provider guarantee. Users configure notifications in their own calendar. No delivery, legal service, statutory deadline or official action is established.

The writer accepts only `date` and `consent: true`. It validates actual dates, leap days, year boundaries and the exclusive following-day end. Year overflow and additional data fields are rejected. Content uses CRLF and 75-octet UTF-8 folding without splitting characters. Control-character injection is rejected. The helper is exposed at `@cornerstone/domain/reminders` without changing the main policy engine.

Standards basis: RFC 5545 sections 3.1, 3.6.1, 3.8.2.2, 3.8.2.4, 3.8.4.7 and 3.8.7.2; https://www.rfc-editor.org/rfc/rfc5545.html. No live calendar-provider behavior is attested.

Verification is in `tests/reminders.test.ts`, `tests/reminder-access.test.ts`, `tests/private/reminders.spec.ts` and `tests/private/reminder-session.spec.ts`. The original browser journey covers consent, actual file bytes, repeat export, revoked access, navigation during a valid held response, accessibility and desktop/mobile layout. New journeys cover actual current-session expiry, successful and non-JSON expired reads held across replacement sign-in, and closing an open form. Held-response fixtures bypass transport abort to exercise the retained session and cancellation boundary. Unit regressions additionally change the session or abort signal after successful validation but before the final file callback and require zero output. Local and remote execution results are recorded separately in the PR and progress checkpoint; a test's presence is not evidence it passed. No migration or protected-production activation is included.

Access-check responses must contain exactly one complete, schema-valid record with the requested ID, the initiating actor/realm context and one capability entry at the same saved version. A success status with only an ID, missing or substituted context, unrelated capabilities, multiple records, an invalid record, a stale version or an unrelated record does not authorize an export. The validation helper returns no case data. The browser scenario additionally checks an ID-only success response. The consent disclosure includes the generation timestamp.
