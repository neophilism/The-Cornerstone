# Workspace sessions and draft access

Migration 005 gives each session a separate opaque inventory identifier. An authenticated person can inspect their active workspace sessions, revoke one, revoke their other sessions, or sign out. The API returns sign-in/expiry times and the current-session flag; it never exposes session-token hashes or claims a verified device or location. Revocation immediately prevents subsequent API authentication. Revocation events are append-only and visible only in the actor's matching realm. Session controls do not supply identity proof, device authority or account recovery.

## Recovering selected session revocations

The account view identifies its authenticated actor, realm and initiating session before displaying the bounded session inventory. Its single-session and “Sign out listed other sessions” controls freeze the exact selected identifiers in memory. The inventory shows up to 100 active sessions; a bulk retry cannot expand its selection to sessions created later or previously outside that page. The current session uses the separate Sign out control.

The selected-session API uses the existing revocation functions and append-only `session_events` table. It validates the live token's actor and realm, checks the initiating session identifier, and processes the fixed targets in a consistent order within one transaction. It returns one existing immutable revocation event for each target, including on replay. A foreign or missing target rejects the entire batch and rolls back any new revocations. Current authentication is checked again before returning historical events. A revoked caller cannot use an old request to recover them.

A lost or mismatched response preserves the exact retry selection. A later denial cannot establish whether the earlier request completed. Confirmation verifies the actor, realm, initiating session, exact target list and one unique event per target. The saved events may describe an earlier request; they do not assert which sessions are active now. A failed subsequent inventory reload leaves the confirmed events visible and hides stale session controls until a fresh read succeeds. Discarding the retry selection or leaving the view forgets only the in-memory request and never undoes a saved revocation.

Inventory refresh clears the previous list while loading. Changed actor, realm or initiating-session context invokes the workspace's existing authenticated refresh. Sign-out, session replacement and view changes invalidate pending inventory and confirmation effects. A current-session 401 clears private workspace state; an earlier request's 401 cannot clear a replacement session. If the initiating session is too old to appear within the existing 100-session inventory, management refuses to guess its identity and requires a new sign-in. No browser persistence, identity-provider setup, device-authority claim or new migration is introduced.

Unit tests verify exact selection, context and event correlation. The actual PostgreSQL identity/access suite covers overlapping batches, one event per session, unchanged historical replay, later-session exclusion, foreign/unknown-target rollback and revoked-caller denial. Desktop/mobile journeys cover lost and substituted responses, denied retries, failed post-confirmation reads, changed HTTP identity, held old inventories and confirmations, and current versus stale expiry. Compiled portal/staff proxy tests verify the selected-session route and unchanged request forwarding after a dropped response. Required CI results establish runtime acceptance.

## Scoped draft access

Scoped draft access is limited to preparation dossiers, organizing groups, event petitions, individual claims and help requests in synthetic development. Only the owner can grant or revoke it, following a sign-in within ten minutes. The owner explicitly consents to access to the record, its saved versions and receipts. The recipient supplies an existing synthetic participant/representative workspace ID; there is no public identity directory or unsolicited invitation message. The server checks the recipient's realm and conflicts without returning profile information.

Access expires within ninety days. Each record permits at most twenty active grants and one active grant per recipient. Read access can optionally include draft editing and synthetic attachment preparation while the record is a draft. It confers no submission, vote, unit transfer, financial execution, privilege escalation or official determination. The recipient must also have the underlying workflow role. Owner actions lock the record, enforce its version, and save the access change, version, receipt, audit and activity event atomically. A repeated command returns its historical receipt.

Revocation or expiry removes future record/version access through RLS and application authorization. Existing downloaded copies cannot be recalled. Conflicts deny both owner and delegate access. The API supplies actions for the exact record version, so a read-only reader sees read/export tools without editing or decision controls. Client controls are a convenience; the server independently enforces every permission.

The isolated PostgreSQL tests cover session isolation, current/other revocation, immutable audit and realm denial; delegation concurrency/idempotency, read-only and editing scope, owner-only grant management, revocation, expiry, recent authentication, conflicts and cross-realm rejection. Browser journeys exercise account controls and grant/read/revoke behavior on desktop and mobile. See PROGRESS.md for verification that has actually completed. Protected production identity and encrypted-recipient workflows remain gated.

## Recovering a completed access change

Receipt replay for a grant or revocation requires current ownership and record visibility. A conflict or transferred record cannot expose its historical access response. Recovering an already committed receipt is read-only and does not require a new recent-authentication window; the current authenticated session and ownership are still required. New grants and revocations continue to require a sign-in within ten minutes.

The PostgreSQL acceptance suite replays a grant after its revocation using an older authentication time, verifies the original historical receipt and unchanged current revoked state, rejects a new change with the same older authentication, and denies both replays after current ownership access is conflicted. Existing receipt-count checks ensure replay did not create another change. This server boundary does not by itself complete browser recovery for the access forms.

## Recovering access changes in the workspace

The grant and revoke forms freeze their exact recipient, permissions, expiration, consent, record version and retry key while an outcome is uncertain. A denied retry does not erase that original intent. Other edits and workspace navigation stay locked until a matching receipt is recovered; the workspace then reloads the current record and grants. Recovering an old grant receipt never displays it as a newly active grant. A definitive rejection of the first request permits correction. Successful confirmation clears the form and requires new consent for another grant.

Recovery intent lives only in this tab. Closing it loses the retry request, not a committed access change. No private request is stored in browser persistence. Current server ownership/visibility checks and recent authentication for new changes remain authoritative. Desktop/mobile journeys cover committed-but-lost grant responses, substituted revocation receipts, denied retries, exact replay, one-grant persistence and refreshed revoked state.

The access panel keeps its expanded state for the same actor, realm and record across confirmation. The record and access controls are removed while current access is checked; only the disclosure preference survives. Refreshed grants are read again from the API, and recipient, scope and consent inputs reset. A different record starts with a closed panel and its own grants. Sign-in, sign-out and session expiry clear the preference. Draft editing is natively disabled while access recovery is pending, in addition to the existing workspace action guard.

## Record reads across session changes

Record pages identify the authenticated requester’s actor and realm, and the workspace verifies that context before using either content or capabilities. Pending direct-reference openings are cancelled by navigation, reference edits and session changes. Current-session expiry still clears private state; late replies from an earlier session cannot reopen its record or sign out a later session. A refresh that observes a changed HTTP session clears the previous actor’s private data before its new page loads, including when that page fails. See [record opening](RECORD_OPENING.md) for response binding, cancellation and the required desktop/mobile regressions.

Record, founding-unit and evidence reference copying also verifies current actor/realm access and retains the initiating session check until the final clipboard call. Changed membership, stale record versions, substituted metadata, cancelled reads and session expiry cannot release a cached reference. See [private references](PRIVATE_REFERENCES.md) for disclosure limits, API compatibility and verification.

## Reviewed file and print sessions

Record downloads, record printing and receipt downloads now carry the same initiating-session boundary through both authenticated reads. Reader context is verified before displaying the complete review, and the retained session check runs again at the synchronous preview or final file/print callback. Record reads additionally require the exact record and matching capability version; receipt reads expose only the actor/realm context and the already-authorized historical receipt. Consent stays bound to the reviewed reader and exact saved bytes. A current 401 clears private state, while an earlier success or non-JSON 401 cannot release content or clear a replacement sign-in. Existing cancellation, renewed consent for changed versions, print cleanup and in-memory-only state remain in force. See [record export](RECORD_EXPORT.md), [record printing](RECORD_PRINTING.md) and [receipt export](RECEIPT_EXPORT.md).
