# Workspace sessions and draft access

Migration 005 gives each session a separate opaque inventory identifier. An authenticated person can inspect their active workspace sessions, revoke one, revoke their other sessions, or sign out. The API returns sign-in/expiry times and the current-session flag; it never exposes session-token hashes or claims a verified device or location. Revocation immediately prevents subsequent API authentication. Revocation events are append-only and visible only in the actor's matching realm. Session controls do not supply identity proof, device authority or account recovery.

Scoped draft access is limited to preparation dossiers, organizing groups, event petitions, individual claims and help requests in synthetic development. Only the owner can grant or revoke it, following a sign-in within ten minutes. The owner explicitly consents to access to the record, its saved versions and receipts. The recipient supplies an existing synthetic participant/representative workspace ID; there is no public identity directory or unsolicited invitation message. The server checks the recipient's realm and conflicts without returning profile information.

Access expires within ninety days. Each record permits at most twenty active grants and one active grant per recipient. Read access can optionally include draft editing and synthetic attachment preparation while the record is a draft. It confers no submission, vote, unit transfer, financial execution, privilege escalation or official determination. The recipient must also have the underlying workflow role. Owner actions lock the record, enforce its version, and save the access change, version, receipt, audit and activity event atomically. A repeated command returns its historical receipt.

Revocation or expiry removes future record/version access through RLS and application authorization. Existing downloaded copies cannot be recalled. Conflicts deny both owner and delegate access. The API supplies actions for the exact record version, so a read-only reader sees read/export tools without editing or decision controls. Client controls are a convenience; the server independently enforces every permission.

The isolated PostgreSQL tests cover session isolation, current/other revocation, immutable audit and realm denial; delegation concurrency/idempotency, read-only and editing scope, owner-only grant management, revocation, expiry, recent authentication, conflicts and cross-realm rejection. Browser journeys exercise account controls and grant/read/revoke behavior on desktop and mobile. See PROGRESS.md for verification that has actually completed. Protected production identity and encrypted-recipient workflows remain gated.

## Recovering a completed access change

Receipt replay for a grant or revocation requires current ownership and record visibility. A conflict or transferred record cannot expose its historical access response. Recovering an already committed receipt is read-only and does not require a new recent-authentication window; the current authenticated session and ownership are still required. New grants and revocations continue to require a sign-in within ten minutes.

The PostgreSQL acceptance suite replays a grant after its revocation using an older authentication time, verifies the original historical receipt and unchanged current revoked state, rejects a new change with the same older authentication, and denies both replays after current ownership access is conflicted. Existing receipt-count checks ensure replay did not create another change. This server boundary does not by itself complete browser recovery for the access forms.

## Recovering access changes in the workspace

The grant and revoke forms freeze their exact recipient, permissions, expiration, consent, record version and retry key while an outcome is uncertain. A denied retry does not erase that original intent. Other edits and workspace navigation stay locked until a matching receipt is recovered; the workspace then reloads the current record and grants. Recovering an old grant receipt never displays it as a newly active grant. A definitive rejection of the first request permits correction. Successful confirmation clears the form and requires new consent for another grant.

Recovery intent lives only in this tab. Closing it loses the retry request, not a committed access change. No private request is stored in browser persistence. Current server ownership/visibility checks and recent authentication for new changes remain authoritative. Desktop/mobile journeys cover committed-but-lost grant responses, substituted revocation receipts, denied retries, exact replay, one-grant persistence and refreshed revoked state.
