# Reviewed synthetic receipt downloads

Receipt downloads require two authenticated reads: one to review the exact historical receipt and one immediately before preparing its file. The user sees the complete file and explicitly consents to an unencrypted copy. The consent is consumed by a download attempt. No cached fallback is available after failed authorization, malformed data or receipt drift.

`GET /receipts?receiptId=…` returns the requesting actor's own synthetic receipt and authenticated reader context after checking current record access in the same restricted database transaction. Its strict wrapper contains only `context: { actorId, realm }` and `receipt`. Record access alone does not expose another actor's receipt through this endpoint. A retained receipt does not override a conflict or revoked grant. The endpoint excludes request keys, audit internals, session tokens and record contents, and creates no new receipt or record version. Historical receipt versions remain valid when the current record has advanced; the UI states that distinction explicitly.

The review retains the requesting reader identifier and checks it and the realm again on confirmation. The reader context is checked independently of the historical receipt fields and is not added to the exported envelope. Missing or substituted context fails closed, so this UI requires the matching receipt API projection.

The versioned JSON envelope identifies a synthetic historical action. A digest is not an independent signature, legal filing or proof of external delivery. The downloaded copy cannot be recalled. Device backups, shared folders and other device users may retain it. Authorization is checked at preparation time, not guaranteed indefinitely after downloading.

Changing workspace context, disabling actions, cancelling, dismissing the receipt or losing the session invalidates pending UI work. Late responses cannot trigger a download after the component is dismissed. No private data is persisted to browser storage.

Both the complete review preview and final file preparation retain the initiating workspace session guard through validation and recheck it at their synchronous disclosure callbacks. This prevents a valid result from being released after a session change in a promise continuation. A held success cannot release a file after another sign-in; a held earlier 401 cannot clear that sign-in, including when the old response body is not JSON. Current-session expiry still clears private state before body parsing.

Verification includes receipt and reader-context substitution, malformed responses, consent checks, final disclosure timing, real PostgreSQL ownership/current-access denial and context projection, historical-version reads without mutation, and desktop/mobile browser download, cancellation, current-session expiry, held earlier responses and accessibility checks. These are source and synthetic runtime tests, not independent certification or protected production activation. Actual required CI results establish runtime acceptance separately from local unit checks and browser collection.
