# Activity delivery and calendar calculations

Migration 004 creates a durable, synthetic in-app inbox. A record command commits its receipt and outbox event together. The worker leases due activity events with `SKIP LOCKED`, a random lease token, a sixty-second lease and at most eight attempts. Expired leases can be recovered. Delivery inserts once per receipt and recipient and marks the event delivered in the same database transaction. Failed attempts use fixed diagnostic codes and bounded exponential backoff; exhausted work stays visibly failed in the operational database.

The worker authenticates as `cornerstone_worker`, a separate restricted role. It receives no record-encryption key, session key or owner connection and has no direct read permission on case records, evidence, sessions or outbox. Only three fixed-search-path database functions can lease, deliver or fail activity work. The API runtime can read its own permitted inbox through RLS and update only `read_at`. A conflict or revoked record access also hides its activity. An activity entry contains opaque record/receipt identifiers, version and action, not private record text.

For local synthetic development, configure `WORKER_DATABASE_URL` with separately provisioned restricted credentials and set `NOTIFICATION_PROVIDER=in-app`. The bootstrap script creates that login on a new isolated database before migrations; it never replaces an existing role's credentials. The additive migration creates a non-login worker role if needed. An owner must provision credentials for that existing role before running a worker. `pnpm dev` then starts the worker alongside the website and API. With the default `disabled` provider, no delivery success is fabricated. No external delivery provider is connected.

The workspace Activity view can refresh updates, open a currently accessible record and persist read status. Marking read is not acceptance of a legal notice. Entries always identify simulation, `classification=activity`, `channel=in_app` and `legalService=false`. This release does not serve legal notices, establish legal service, start response deadlines or record external delivery acceptance.

The domain calendar helpers validate exact calendar dates, IANA jurisdiction timezones, bounded periods and offset-bearing instants. Day periods use calendar dates rather than elapsed twenty-four-hour intervals. The anniversary helper exposes an explicit leap-day choice; existing compact calculations retain their February 28 default. A candidate deadline requires a reviewed rule version and a service-evidence identifier and never makes an automatic default decision. These are pure calculations: institutional authority, the actual evidence, legally sufficient service, holiday/weekend adjustments and state-specific rules must be validated by the future legal-service workflow. A caller assertion is not that verification.

Verification includes actual PostgreSQL worker privileges, recipient isolation, read persistence, concurrent dispatch, stale-token rejection, expired-lease recovery, bounded failures, and browser activity behavior. Calendar tests cover DST boundaries, leap years, invalid dates and rejection of ordinary activity as a deadline trigger. See PROGRESS.md for the last CI run actually completed.

## Membership and assigned-review updates

Additive migration 010 extends in-app delivery to currently assigned reviewers and active read delegates. An association submission notifies its invited founders; closure and restoration updates notify active unit holders. Opening or tallying a member decision notifies the frozen roll's current unit holders. Conflicts and current record access still control visibility. The keyless restricted worker retains its existing three-function interface and receives no private record text or ballot choices.

Personal founding responses and ballots are not broadcast to every member. Owner/actor activity and legitimate assigned-review or delegated access remain as before. Delivery stays idempotent per receipt and recipient. If a valid event has no unconflicted recipient, it can finish with zero inserts rather than retrying indefinitely. None of these updates is legal service, external delivery acceptance, consent or a payment.

An invitation or founding unit can open its association even when that record is outside the page currently loaded in My records. Opening rechecks current permission. The list of member decisions explicitly identifies its loaded-record scope; older records remain available in My records.

The membership PostgreSQL journey verifies invited-founder and assigned-review delivery, exclusion of unassigned staff, closed-roll and voting updates, conflict hiding, and no broad broadcast of a personal response or ballot. A desktop/mobile test omits an invitation's association from the initial loaded page and verifies that its reference still opens through the real scoped endpoint. Migration 010 must pass this acceptance before application to the Neon development branch; production remains unmigrated.
